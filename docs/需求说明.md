# OPC 内部创作者管理平台需求说明

> 状态：核心需求与主技术路线已确认，功能细节仍为初始草案。除“已确认需求”外，本文内容均为讨论建议，尚不构成已批准的实施范围。

- 用户已确认退出探索模式并开始正式开发，先搭建统一平台并接入企业登录。
- 统一平台命名为“信计 X 平台 / SinX Platform”，与创作者平台是两个独立系统，分别拥有前后端、数据库和后续部署。
- 第一迭代为飞书 / 企业微信登录、平台成员与会话、无侧栏工作台和退出。统一平台已部署到 x.aixmax.cn，企微应用已配置，真实登录、工作台刷新、退出与匿名拦截已验证；飞书尚未配置。

- 外部创作者资料公司共享；维护人表示运营职责，不作数据隔离。登录账号与创作者档案分开。
- 此段为后续明确确认，覆盖下文草案中与之冲突的初始建议。实际交付与运行说明见 ../sinx-platform/README.md。

## 一、已确认需求

- 建设一个供公司内部使用的创作者管理平台。
- 主要使用者为内部运营人员。
- 主要管理对象为公司的 OPC 用户，重点登记外部职业创作者，例如编剧、剪辑师。
- 核心诉求是登记与管理外部创作者资源。
- 主技术路线沿用 `ant_short_TV` 的 React/Umi、Ant Design、Java Spring Boot、MySQL 和腾讯云 COS 私有对象存储，详见 [技术选型.md](技术选型.md)。此确认不代表全部建议功能已获批准。

OPC 的准确业务定义尚未确认。本文暂按“公司维护的外部创作者资源”描述管理对象，不扩展其组织形式、雇佣关系或法律身份。

## 二、建议的产品定位

定位为“内部创作者资源与合作管理平台”，优先解决以下问题：

- 公司有哪些创作者资源？
- 每个人擅长什么，有哪些可参考的作品？
- 谁适合当前需求，报价与档期是否合适？
- 谁负责维护，最近沟通过什么？
- 过去合作过哪些项目，交付情况如何？

建议先做好内部管理，不将外部社区、内容发布或即时聊天作为第一版默认目标。

## 三、使用者与管理对象（建议）

### 内部使用者

- 管理员：维护内部账号、权限与基础配置。
- 运营负责人：查看团队资源、分配维护负责人、了解合作情况。
- 运营人员：在授权范围内登记创作者、维护资料与跟进合作。
- 业务查看人员：查找创作者与作品，联系方式、报价等信息按权限开放。

以上角色划分及其数据范围待确认，查看、编辑和导出权限应分别考虑。

### 外部创作者

第一版建议将外部创作者作为资源档案管理，不强制开通系统账号。是否提供外部填报、资料更新或登录入口，需结合实际运营方式确认。

## 四、核心功能（建议）

### 4.1 创作者资源库

一位创作者保留一份统一档案，可关联多个职业。建议的信息类别：

| 类别 | 字段示例 |
| --- | --- |
| 基础资料 | 姓名或艺名、城市、联系方式、简介、来源渠道 |
| 职业能力 | 主职业、其他职业、技能、擅长题材、使用工具 |
| 作品与经历 | 作品名称、链接或附件、担任角色、相关经历 |
| 合作条件 | 报价区间、币种、计价单位、远程或驻场、可接单情况 |
| 运营信息 | 维护负责人、最近联系时间、下次跟进时间 |
| 历史记录 | 沟通记录、合作项目、交付情况与反馈 |

字段必填性、字段权限和数据字典待确认。报价必须与计价单位一起解释，不能直接比较不同单位的金额。

职业专属信息示例：

- 编剧：短剧、长剧或广告方向，擅长题材，原创或改编能力，剧本案例，按集或按项目报价。
- 剪辑师：短视频、短剧或宣传片方向，使用软件，调色与包装能力，剪辑案例，按条、分钟或天报价。

具体职业分类与专属字段需由实际业务确认。

### 4.2 搜索与筛选

- 按姓名、联系方式及作品名称搜索。
- 按职业、技能、题材、城市、报价条件和接单状态组合筛选。
- 按维护负责人、最近联系时间、是否合作过筛选。
- 如纳入项目管理，可将创作者加入项目候选名单。

职业、技能和题材标签建议统一维护，减少同义词和重复标签。

### 4.3 运营跟进

记录沟通时间、沟通人员、沟通内容、合作意向、报价或档期变化、后续事项和下次跟进时间。

建议独立管理以下状态，具体枚举待确认：

| 状态维度 | 示例 | 归属对象 |
| --- | --- | --- |
| 资源阶段 | 待核实、已核实、重点维护、暂不合作 | 创作者档案 |
| 接单状态 | 可接单、需预约、暂不接单、未知 | 创作者档案 |
| 合作状态 | 候选中、沟通中、已确认、合作中、已完成 | 某次项目合作 |

同一创作者可以同时参与多个项目，不应以某个项目的合作状态覆盖整体接单状态。

### 4.4 轻量项目与合作记录

建议流程：创建项目需求、筛选候选创作者、沟通确认、记录合作与交付、填写反馈。

合作记录建议包含项目、创作者、承担工作、约定报价与单位、合作时间、交付情况、评价人和反馈依据。

反馈维度可包括交付质量、按时交付情况、沟通配合和再次合作意愿；避免只用一个综合分数判断人才能力。

### 4.5 批量导入与资料维护

- 提供统一导入模板，导入前预览并校验。
- 根据手机号、邮箱等提示疑似重复，由人工确认，不自动合并。
- 显示资料更新时间，特别是报价与档期的最近确认时间。
- 提供归档能力，重要修改、导出及归档保留操作记录。

## 五、建议页面结构

- 工作台：个人待跟进事项、近期合作、资料待完善提醒。
- 创作者资源库：列表、搜索筛选、新增、详情、批量导入。
- 项目与合作：需求、候选名单、合作记录。
- 跟进记录：沟通历史与跟进安排。
- 基础配置：职业、技能、题材与来源渠道。
- 系统管理：内部账号、角色权限与操作日志。

列表页优先支持快速找人；详情页集中展示职业能力、作品、跟进和合作记录。

## 六、数据与权限约束（建议）

- 明确人才资源是全公司共享、团队共享还是按负责人隔离，不预设最终规则。
- 联系方式、报价、内部评价和批量导出应有明确权限。
- 第一版原则上不收集身份证、银行卡等与资源登记无直接关系的信息。
- 作品与附件的使用授权、可见范围和存储方式需明确。
- 数据采集目的、保存期限、纠错及删除流程需结合公司制度与适用要求确定。
- 原型、演示和测试采用虚构个人资料，不使用真实创作者联系方式。

## 七、第一版范围建议

建议优先实现：

1. 内部账号与基础权限。
2. 创作者档案新增、编辑、查看和归档。
3. 多职业、标签与作品管理。
4. 搜索筛选和批量导入。
5. 负责人、跟进记录与待办。
6. 轻量项目合作记录及反馈。

建议暂不纳入：外部社区、内容发布、即时聊天、自动结算、复杂项目排期和智能匹配。外部登录、合同及结算管理是否需要，应另行确认。

## 八、建议验收场景

以下用于后续确认范围后的验收设计，不代表当前已有实现：

- 运营可登记一名同时具备编剧与剪辑能力的创作者，且不会产生两份独立人才档案。
- 运营可组合筛选职业、题材与接单状态，查看匹配结果及作品。
- 运营可记录一次沟通并设置下次跟进时间。
- 同一创作者关联多个项目时，各项目的合作状态互不覆盖。
- 无授权的人员不能查看受限联系方式或执行批量导出。
- 导入疑似重复或格式错误的数据时，可在确认入库前识别问题。

## 九、待确认事项

- OPC 在公司业务中的准确含义与管理边界。
- 实际运营人数、团队划分、创作者数量及预计增长量。
- 当前使用的表格或系统、存量字段、导入格式与迁移需求。
- 首批职业类别、每类职业的字段与必填项。
- 资源共享范围、负责人分配规则与敏感字段权限。
- 是否需要外部创作者自行填报或登录。
- 第一版是否包含项目、合同、结算及审批。
- 是否接入公司现有登录体系。
- 精确依赖版本与配套组件、部署环境、COS 地域与访问配置、备份及维护责任。

## 十、当前实现状态

仓库已包含需求文档、HTML 原型与 sinx-platform/ 统一平台独立工程，具体依赖、启动命令和验证边界见该目录 README。统一平台首个登录切片已部署并完成真实企微验收。

新增手动成员管理：管理员创建和编辑成员、设置角色及启用状态、核对待关联账号并关联到成员、解除关联、查看操作记录。企业授权成功不等于平台准入；必须关联到已启用的平台成员才能登录，未关联身份只进入待关联列表。一个成员可关联飞书及企微身份，不按姓名、手机号自动合并。角色和状态变更使旧会话失效，最后一位可登录管理员受保护。初始管理员通过显式部署配置预先关联。

已实现独立创作者第一版：公司共享档案的新增、编辑、详情、职业/标签/城市筛选、搜索分页、作品链接、归档恢复及操作记录，经统一平台OAuth2授权码+PKCE登录。维护人默认本人，可选启用成员，不作为数据隔离条件。外部人员不是登录账号。本期不含文件上传、导入、跟进、项目、合同或结算。可配置应用管理、全量通讯录同步及自动匹配尚未实现。部署及实际验收状态见 sinx-platform/docs/server-deployment.md，依赖审计及密钥轮换仍按记录处理。

原型结构对齐补充：创作者独立业务侧栏包含资源库、职业分类、技能标签、角色权限；统一平台保持无侧栏。档案新增个人简介及参考报价，详情与编辑恢复两栏和分组；筛选及页码经URL保留。职业/标签/来源配置真实持久化，仅管理员维护，引用名称不可直接改名；角色页展示固定ADMIN/MEMBER规则，不实现自定义角色。全部/近7日更新/归档计数来自真实档案，新增维护人与来源筛选。不包含职业动态字段引擎或批量导入导出。
